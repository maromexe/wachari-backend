Wachari — архітектура бекенду

Цільова схема wachari-backend (ASP.NET Core 9): з яких частин складається API, які дані зберігаються, які є ендпоінти і як проходять основні сценарії. Позначки «готово / в роботі / заплановано» відповідають крокам, які ми вже пройшли.

1. Загальна схема

Фронтенд звертається лише до нашого API. API — єдиний, хто працює з базою SQL Server і з TMDB. Постери браузер бере напряму з CDN TMDB, без участі бекенду.

2. Шари і структура папок

Запит завжди йде згори вниз: контролер → сервіс → DbContext / клієнт. Шар бачить лише той, що під ним, тому контролер не пише SQL, а сервіс нічого не знає про HTTP-статуси.

Хто за що відповідає

  • Controllers — маршрути, приймають Request DTO, повертають статус-код і Response DTO. Логіки немає.
  • Dtos — контракт API: що приходить (…Request) і що віддаємо (…Response). Сутності з бази назовні не виходять.
  • Services — бізнес-правила: «не можна додати друга двічі», «переглянуте не рекомендуємо».
  • Data — WachariDbContext, конфігурація таблиць, міграції, сідер.
  • Models — сутності EF Core (таблиці).
  • Integrations — клієнти зовнішніх API (TMDB, Python-сервіс) за інтерфейсами, щоб у тестах їх можна було підмінити.
  • Middleware — глобальна обробка винятків → ProblemDetails.

3. Модель даних

П'ять таблиць у SQL Server. MediaItems лишається однією таблицею з дискримінатором Type (TPH), як зараз.

Що зміниться в наявних моделях

  • PosterUrl → PosterPath: зберігаємо лише шлях від TMDB, повна адреса збирається в Response DTO.
  • Додаються TmdbId і UpdatedAt, унікальний індекс на (TmdbId, Type).
  • List<string> Genres → окрема таблиця Genres зі зв'язком N:M, щоб фільтрувати й рахувати рекомендації за жанрами в SQL.

Чого навмисно немає

  • Картинок у базі: постери віддає CDN TMDB.
  • Друзів: відкладено (розділ 8). Результатів рекомендацій: вони рахуються на кожен запит.
  • Акторів, режисерів, трейлерів: за потреби беруться з TMDB на сторінці деталей.

5. Основні сценарії

Вхід

  1. POST /api/auth/login з email і паролем.
  2. AuthService знаходить користувача, BCrypt.Verify порівнює пароль із хешем.
  3. TokenService підписує JWT: claims sub (Id), name, role, термін дії.
  4. Фронтенд зберігає токен і додає до кожного запиту заголовок Authorization: Bearer <token>.
  5. Middleware перевіряє підпис і термін; у контролері Id береться з User (claims), а не з тіла запиту.

Знайти фільм і позначити переглянутим

  1. GET /api/tmdb/search?query=nosferatu → TmdbClient перевіряє кеш, інакше йде в TMDB.
  2. Користувач обирає результат: POST /api/media/import { tmdbId, type }.
  3. MediaService шукає (TmdbId, Type) у базі; якщо немає, тягне деталі з TMDB, зберігає з жанрами і повертає наш id.
  4. PUT /api/me/library/{id} { status: "Watched", userRating: 9 }.
  5. Далі каталог, деталі й рекомендації читають цей фільм з нашої бази.

Оновлення даних з TMDB

  1. Фільм уже є в нашій базі, але рейтинг у TMDB змінюється з часом.
  2. При POST /api/media/import для існуючого запису MediaService дивиться на UpdatedAt.
  3. Якщо запис старший за 7 днів, бере свіжі деталі з TMDB і оновлює поля та жанри; інакше повертає як є.
  4. Каталог і сторінка деталей завжди читають лише нашу базу, тому недоступність TMDB їх не ламає.

Рекомендації (проста версія)

  1. Після реєстрації користувач шукає і обирає 10–15 улюблених фільмів → PUT /api/me/liked.
  2. GET /api/recommendations: RecommendationService бере з бази улюблені фільми і кандидатів — усі MediaItems, яких немає в бібліотеці користувача.
  3. Щоб кандидатів було достатньо, .NET попередньо імпортує з TMDB популярні фільми трьох найчастіших жанрів серед улюблених (/discover).
  4. Python будує профіль користувача і рахує score кожного кандидата (алгоритм нижче).
  5. .NET ще раз відкидає переглянуте, підтягує дані з бази і повертає Response DTO за спаданням score.

Алгоритм у Python

  1. Жанри: вектор частот жанрів серед улюблених (наприклад, Crime 0.4, Drama 0.3…). Схожість кандидата — косинус між цим вектором і жанрами кандидата.
  2. Опис: TF-IDF по overview (scikit-learn), схожість кандидата — середній косинус до улюблених.
  3. score = 0.6·жанри + 0.3·опис + 0.1·(Rating / 10).
  4. Без навчання моделі і без власної бази — сервіс без стану, ~100 рядків коду.

Помилка в будь-якому місці

  1. Валідація DTO не пройшла → [ApiController] сам повертає 400 з errors.
  2. Сервіс кидає власний виняток (NotFoundException, ConflictException).
  3. ExceptionHandlingMiddleware перетворює його на 404 / 409 у форматі ProblemDetails.
  4. Будь-який інший виняток → 500 без деталей стеку назовні; деталі пишуться в лог.

6. Домовленості API

Статус-коди

  • 200 дані · 201 створено + Location · 204 успіх без тіла
  • 400 невалідний запит · 401 немає/прострочений токен · 403 токен є, прав немає
  • 404 не знайдено · 409 конфлікт (дублікат)
  • 409 також «ще не обрано 10 улюблених» · 502 помилка TMDB · 503 недоступний Python-сервіс

Формати

  • JSON у camelCase, дати як "1994-10-14".
  • Пагінація: ?page=1&pageSize=20 → { items, page, pageSize, totalCount }, pageSize не більше 50.
  • Помилки — стандартний ProblemDetails: { type, title, status, errors? }.
  • Назовні лише Response DTO; постер — повна URL: https://image.tmdb.org/t/p/w342{posterPath}.

Конфігурація і секрети

  • appsettings.json: Jwt:Issuer, Jwt:Audience, Tmdb:BaseUrl, Recommender:BaseUrl, дозволені CORS-origin.
  • User Secrets (не в Git): ConnectionStrings:DefaultConnection (у ньому пароль SQL Server), Jwt:Key, Tmdb:ApiKey.
  • Налаштування читаються через Options-класи (TmdbOptions, JwtOptions).

Документація і тести

  • OpenAPI (/openapi/v1.json) + Scalar або Swagger UI в Development.
  • Wachari.Api.http — ручні запити з Rider.
  • Пізніше: проєкт tests/Wachari.Api.Tests (xUnit) для сервісів з підміненими ITmdbClient і IRecommenderClient.

База даних: SQL Server і SSMS

Як це запускається

  • Windows: SQL Server Developer Edition (безкоштовний) + SSMS. Рядок підключення: Server=localhost;Database=Wachari;Trusted_Connection=True;TrustServerCertificate=True.
  • MacBook: SQL Server не встановлюється напряму і SSMS під macOS немає. SQL Server запускається в Docker-контейнері, а таблиці переглядаються через вкладку Database у Rider. Рядок підключення: Server=localhost,1433;Database=Wachari;User Id=sa;Password=…;TrustServerCertificate=True.
  • Код застосунку на обох комп'ютерах однаковий, відрізняється лише рядок підключення в User Secrets.

Що зміниться в проєкті

  • Пакет Microsoft.EntityFrameworkCore.Sqlite → Microsoft.EntityFrameworkCore.SqlServer, у Program.cs UseSqlite → UseSqlServer.
  • Наявні міграції згенеровані під SQLite (типи TEXT, INTEGER), тому папку Migrations/ видаляємо і створюємо нову InitialCreate під SQL Server.
  • Тестові дані знову заповнить DbSeeder; wachari.db більше не потрібен.
  • Для Rating задаємо точний тип decimal(3,1), для рядків — максимальну довжину, щоб не було nvarchar(max) всюди.

8. Відкладено

Друзі

Таблиця Friendships (Requester, Addressee, Status Pending/Accepted), заявки в друзі, пошук користувачів, перегляд бібліотеки друга. Тоді в Python-сервіс додасться ще один вхід — улюблене друзів з меншою вагою.

Розумніші рекомендації

Колаборативна фільтрація («кому сподобалось те саме, сподобалось ще…»), врахування оцінок 1–10 замість лише «подобається», кешування результатів. Має сенс, коли буде багато користувачів.
